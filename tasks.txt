[x] TASK P0-01 - Restore a valid Alembic migration chain
Priority/Impact/Complexity/Risk: P0 / Critical / M / High

Tests: migration smoke test on PostgreSQL plus schema assertions for users, credentials, appointments, call analytics, and overlap indexes.

[x] TASK P0-02 - Authenticate Twilio HTTP webhooks
Priority/Impact/Complexity/Risk: P0 / Critical / S / Medium
Problem: Anyone can invoke call and recording endpoints as if they were Twilio.
Evidence: `twilio_inbound_voice()` and `twilio_recording()` in `backend/app/telephony/router.py` pass form data to `backend/app/telephony/service.py` without validating `X-Twilio-Signature`; the CSRF middleware exempts these webhook paths.
Recommended implementation: validate the signature using Twilio's official request validator over the externally visible URL and exact form payload before any side effect; configure trusted public base URL/proxy handling; reject absent/invalid signatures uniformly and add replay/idempotency protection for state-changing callbacks. Reference: https://www.twilio.com/docs/usage/webhooks/webhooks-security
Affected files/modules: `backend/app/telephony/router.py`, `backend/app/telephony/service.py`, `backend/app/core/config.py`, reverse-proxy configuration, Twilio route tests.
Migration/config/rollback: add an explicit externally visible webhook base URL or a strictly trusted forwarded-header policy; no data migration. Roll back only after disabling public webhook delivery.
Acceptance criteria: valid signed webhook succeeds; altered URL/body, missing header, and invalid signature return 403 with no database/network side effect; duplicate callback is harmless.
Tests: official-style signature fixtures, proxy URL cases, tampering, replay, and tenant-isolation integration tests.
Dependencies: deployment must know the canonical HTTPS webhook URL.

[x] TASK P0-03 - Bind voice WebSockets to persisted call ownership
Priority/Impact/Complexity/Risk: P0 / Critical / M / High
Problem: A caller can supply another user's ID and gain that tenant's voice tools and calendar credentials.
Evidence: `voice_websocket()` in `backend/app/voice/gateway.py` accepts `/ws/voice` immediately; `resolve_call_context_from_start()` in `backend/app/telephony/service.py` trusts `customParameters.user_id` and skips `CallSession` ownership lookup when it is present.

Affected files/modules: `backend/app/voice/gateway.py`, `backend/app/voice/session.py`, `backend/app/telephony/service.py`, `backend/app/db/models.py`, tests.
Migration/config/rollback: likely add hashed token/expiry/consumed fields or a Redis record with TTL; migration required if persisted. Deploy webhook producer before enforcing consumer, within one coordinated release.
Acceptance criteria: caller-supplied user IDs are ignored; tokens are tenant-bound, expiring, and one-use; unknown/mismatched CallSid cannot reach Deepgram or any tool; socket is not accepted before verification.
Tests: forged user ID, replayed token, expired token, mismatched CallSid, concurrent consume, and valid-call integration cases.
Dependencies: P0-02; coordinate with P2-01 call lifecycle.

[x] TASK P0-04 - Harden recording ingestion against SSRF and unsafe files
Priority/Impact/Complexity/Risk: P0 / Critical / M / High
Problem: Attacker-controlled recording metadata can forward Twilio credentials to arbitrary hosts and write outside the intended temporary directory.

Migration/config/rollback: configurable maximum bytes/timeouts and optional Twilio host allowlist; no schema migration.
Acceptance criteria: non-Twilio URL, redirect, malformed SID, oversized/non-audio body, and ownership mismatch fail before credential disclosure or filesystem escape; valid recording is processed and removed.

[x] TASK P0-06 - Preserve context and safe database ownership in voice tools
Priority/Impact/Complexity/Risk: P0 / Critical / M / High
Problem: Voice tool calls lose tenant context in worker threads and reuse a synchronous SQLAlchemy session across threads.
Evidence: `backend/app/voice/session.py` uses a custom `ThreadPoolExecutor` through `run_in_executor`; `ContextVar` values do not propagate with that call, while tools read `current_call_context`, `voice_user_id`, and `voice_db`. The session is created outside the executor that uses it.
Recommended implementation: pass an immutable explicit tool context rather than ambient globals; execute each synchronous tool via `asyncio.to_thread` or copied context; create/close its SQLAlchemy session inside the executing thread; never share a Session concurrently.
Affected files/modules: voice session, tool registry/handlers, database session factory, tool tests.
Migration/config/rollback: no migration; retain public tool schemas while changing internal invocation.
Acceptance criteria: every tool receives the authenticated call/user context; no Session crosses thread boundaries; cancellation closes sessions; concurrent calls use distinct context.
Tests: executor context regression, two-tenant concurrency, session close on success/error/cancel, and end-to-end tool call.
Dependencies: P0-03.

[x] TASK P0-07 - Enforce one atomic booking policy for every channel
Priority/Impact/Complexity/Risk: P0 / Critical / L / High
Problem: Voice booking bypasses business hours, service duration, buffers, and local conflicts; all paths use check-then-write and can double-book under concurrency.
Evidence: `create_appointment()`/`update_appointment()` in `backend/app/appointments/router.py` invoke `backend/app/appointments/policy.py`; voice `create_calendar_event()`/`reschedule_appointment()` in `backend/app/calendars/tools.py` mutate Google/local state without those policy checks. `validate_slot()` and the later insert are not serialized, and the new B-tree overlap index cannot enforce arbitrary interval exclusion.
Recommended implementation: route HTTP and voice create/reschedule through one domain service; validate timezone-aware duration, hours, buffers, provider availability, and local/external conflicts; serialize per tenant/calendar using PostgreSQL advisory locks or a reservation transaction, then re-check inside the lock.
Affected files/modules: appointment service/routes/schemas, voice tools, booking policy helpers, models/repositories, tests.
Migration/config/rollback: advisory-lock approach needs no schema change; if reservation rows are chosen, add an expiring-state migration and cleanup. Preserve API response contracts.
Acceptance criteria: identical input has identical policy result over HTTP and voice; two concurrent overlapping requests yield exactly one booking; reschedule cannot create a conflict; DST cases are deterministic.
Tests: policy characterization, HTTP/voice parity, PostgreSQL concurrency integration, business-hour/buffer/DST/reschedule cases.
Dependencies: P0-01 and P0-06.

[x] TASK P0-08 - Make external and local appointment writes idempotent
Priority/Impact/Complexity/Risk: P0 / Critical / M / High
Problem: Failure between Google event creation and local insert can create duplicate or orphaned calendar events.
Evidence: voice `create_calendar_event()` in `backend/app/calendars/tools.py` computes an idempotency key and checks the local row, but calls `calendar_service.create_event()` before `backend/app/appointments/service.py` commits that row; a crash in between leaves no durable pre-provider operation state to distinguish/reconcile the already-created event.
Recommended implementation: create a local pending operation with a client/request idempotency key, perform the provider write once, then finalize locally; retries resume from recorded state. Add a bounded reconciliation job for pending/failed operations and use provider event IDs as unique tenant-scoped identifiers.
Affected files/modules: appointment model/service/repository, Google provider, Celery tasks, API/voice callers, tests.
Migration/config/rollback: add operation state/idempotency uniqueness if absent; backfill existing rows as completed; downgrade only after pending operations are drained.
Acceptance criteria: retrying the same request creates one local row and one Google event; crash at each boundary is recoverable; unresolved operations are visible and retried with limits.
Tests: injected failure before/after provider call, duplicate/concurrent key, reconciliation, provider timeout ambiguity.
Dependencies: P0-01 and P0-07.

[x] TASK P1-01 - Make Twilio call synchronization lossless and refresh active calls
Priority/Impact/Complexity/Risk: P1 / High / M / Medium
Problem: A burst over 100 calls can be skipped and the newest/active call may never be refreshed.
Evidence: `fetch_and_store_twilio()` in `backend/app/analytics/service.py` calls `TwilioProvider.fetch_calls(limit=100, start_time_after=user.twilio_last_synced_at)` and advances the cursor to the newest returned start time; `backend/app/telephony/providers/twilio.py` does not expose page traversal or active-call refresh.
Recommended implementation: follow Twilio pagination to exhaustion within bounded job budgets; persist a stable cursor with overlap lookback; upsert by CallSid; always revisit nonterminal calls until terminal; advance cursor only after a completed page transaction.

Migration/config/rollback: add cursor/job metadata only if current state cannot represent page progress; make page/budget/lookback configurable.

[x] TASK P1-02 - Replace per-call lookup/commit with PostgreSQL bulk upsert
Priority/Impact/Complexity/Risk: P1 / High / M / Medium
Problem: Synchronization performs an avoidable SELECT and transaction commit for every call.
Evidence: `upsert_twilio_calls()` in `backend/app/analytics/service.py` performs one `SELECT` by `(user_id, sid)` for every input call before one final commit, producing N+1 query round trips and ORM objects.
Recommended implementation: normalize a page, then use PostgreSQL `INSERT ... ON CONFLICT ... DO UPDATE` on the tenant-scoped call identity in batches; commit once per page and preserve newer local terminal data using explicit update rules.
Affected files/modules: call analytics repository/model, Twilio sync task, tests.
Migration/config/rollback: ensure an appropriate unique constraint such as `(user_id, call_sid)`; migration required if missing. Old code is the rollback path only within a deployment rollback, not a permanent fallback.
Acceptance criteria: query count is constant per page; repeat sync is idempotent; mixed inserts/updates match existing semantics; failure rolls back the page.
Tests: SQL query-count assertion on PostgreSQL, repeat/mixed batch, timestamp conflict, rollback.
Dependencies: P0-01 and P1-01.

[x] TASK P2-02 - Add bounded Deepgram reconnect and safe audio degradation
Priority/Impact/Complexity/Risk: P1 / High / M / High
Problem: A transient Deepgram failure ends the call because the first completed bridge task cancels the rest; failure classes have no recovery policy.
Evidence: `VoiceSession.run()` in `backend/app/voice/session.py` waits with `asyncio.FIRST_COMPLETED` and cancels sibling Twilio/Deepgram tasks; `backend/app/voice/providers/deepgram.py` has no reconnect state machine or failure classification.
Recommended implementation: classify authentication/configuration failures as terminal and network/service failures as retryable; reconnect with bounded exponential backoff and total deadline; buffer only a small safe inbound window; announce a brief fallback then transfer/end cleanly after budget.
Affected files/modules: Deepgram client/session bridge, voice state, configuration, tests.
Migration/config/rollback: add retry count/backoff/deadline/buffer settings; no migration.
Acceptance criteria: one transient disconnect recovers without cross-call audio; permanent credentials fail fast; retry exhaustion gives a controlled caller experience and terminal session reason; buffers are bounded.
