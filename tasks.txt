# PHASE 1 — Repair secure-link and payment flow end-to-end

This is a critical correctness/security phase.

Current backend creates URLs similar to:
`/secure/{purpose}?t=<raw token>`

but the React router has no matching customer-facing route.

Files likely involved:

* `backend/app/notifications/secure_links.py`
* `backend/app/notifications/secure_link_worker.py`
* `backend/app/db/models.py`
* `backend/app/payments/api.py`
* `backend/app/payments/service.py`
* `backend/app/payments/providers.py`
* `backend/requirements.txt`
* Alembic migration
* `frontend/src/app/router.tsx`
* new `frontend/src/api/payments.ts`
* new `frontend/src/pages/SecurePaymentPage.tsx`
* supporting frontend components/tests
* backend secure-link/payment tests

Subtask 1.1 — Secure-link route
Add a PUBLIC frontend route:
`/secure/:purpose`

It must not require the normal application login.

Support at minimum:

* loading;
* invalid token;
* expired token;
* pending payment;
* already paid;
* payment failed;
* Stripe redirect;
* manual-token capture when applicable.

Never trust `?status=success` as payment proof.
Stripe webhook/provider state remains authoritative.

Subtask 1.2 — Token storage
`SecureLinkDelivery.token_ciphertext` must use the repository's existing `EncryptedText` mechanism instead of a plain String.

Do not persist a full raw-token URL in `metadata_json`.

Persist:

* token hash for lookup;
* encrypted raw token only while needed for delivery.

Build the external URL at delivery time.

Provide a safe migration/backward-compatibility path for existing rows.

If practical, allow encrypted delivery token material to be cleared after confirmed transport submission.

Subtask 1.3 — Fix expired-row starvation
The current worker must not select expired `scheduled` rows forever.

Expired rows must transition deterministically to an expired/failed terminal state.

Test the pathological case:

* create >50 expired rows;
* create a valid scheduled row after them;
* run delivery;
* prove the valid row is eventually processed.

Subtask 1.4 — Prevent duplicate delivery
Do not hold a DB transaction open during Twilio/SMTP network I/O.

Implement durable claim/lease semantics, for example:

* atomically select/claim eligible rows;
* status `processing`;
* claim token and claim expiry or equivalent;
* commit;
* perform provider I/O;
* transition to `sent` or retryable/failed;
* reclaim abandoned processing rows after lease expiry.

Use PostgreSQL `FOR UPDATE SKIP LOCKED` or another correct atomic claiming strategy where appropriate.

Add a concurrency test proving two workers cannot both claim/send the same delivery.

Subtask 1.5 — Correct channel handling
Never fall through from an SMS delivery to sending an email to a phone-number recipient.

Rules:

* `sms` requires a usable SMS transport;
* `email` requires a usable email transport;
* absence of the requested transport returns a bounded `transport_unavailable` failure/retry condition.

Resolve Twilio credentials from the appropriate tenant integration rather than relying solely on process-global Twilio settings.

Do not copy authentication secrets into delivery metadata.

Subtask 1.6 — Complete Stripe support
Add the stable pinned Stripe SDK to `backend/requirements.txt`, consistent with this repository's pinned dependency policy.

The currently intended stable version is `stripe==15.6.1` unless repository compatibility testing requires a different stable 15.x release.

Change provider creation so the application retains:

* provider Checkout Session ID;
* browser-usable Checkout URL.

Do not expose arbitrary provider metadata publicly.

The token-authenticated secure-payment endpoint may expose only the safe data needed by the payment page.

For Stripe:

* customer opens secure page;
* frontend receives/requests safe Checkout URL;
* browser redirects to Stripe;
* Stripe webhook captures the payment;
* returned frontend page displays/polls authoritative payment status.

Add tests for missing Stripe configuration and webhook completion.

# PHASE 2 — Remove blocking bottlenecks without async-ORM migration

## 2.1 Twilio and Stripe async endpoints

Files:

* `backend/app/telephony/router.py`
* `backend/app/payments/api.py`

## 2.3 Parallelize independent voice read tools

Files:

* `backend/app/voice/session.py`
* `backend/app/voice/tool_runtime.py`
* registry metadata/tests

The registry already classifies tools as READ or MUTATION.

Currently all function calls inside one provider FunctionCallRequest are awaited sequentially.

Implement batching with mutation barriers.

Example:
READ A
READ B
READ C

=> run concurrently using `asyncio.gather` through the EXISTING bounded tool runtime.

Example:
READ A
MUTATION B
READ C

=> A may run first;
=> mutation B must remain serialized and complete before dependent later work;
=> C must not be reordered across B unless dependency safety can be formally established.

Never parallelize independent mutation side effects merely for speed.

Preserve:

* tool-result idempotency;
* reconnect replay protection;
* function IDs;
* error envelopes;
* context propagation;
* bounded executor admission.

Measure sequential versus batched read latency in tests/benchmark.
