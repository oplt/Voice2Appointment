# Phase 1 — Reservation concurrency correctness

### Status: 🔴 HIGH PRIORITY

The new reservation engine is one of the strongest additions, but I see a potentially important race.

Resource usage is calculated by querying overlapping reservations:

```text
existing.start < requested.end
AND
existing.end > requested.start
```

and summing resource quantities.

That is correct logically.

The problem is the locking granularity. The new scheduling lock includes an hourly `start_bucket`. Therefore:

```text
Reservation A:
10:50 → 11:50
lock bucket = 10

Reservation B:
11:00 → 11:30
lock bucket = 11
```

These reservations overlap but can acquire **different advisory locks**.

There is also no database-level exclusion constraint protecting overlapping `reservation_resource` ranges; the migration adds a normal window index and idempotency constraint only.

The current Phase 5 tests check conflicting bookings sequentially using SQLite; they do not reproduce two real PostgreSQL transactions starting simultaneously across bucket boundaries.

### Recommended fix

Don't lock by start hour alone.

A safer hierarchy is:

```text
single resource
    ↓
lock resource_id
    ↓
validate entire overlapping time range

capacity pool
    ↓
lock capacity_pool/resource_id
    ↓
calculate overlapping consumption
    ↓
allocate
```

For high-value resource types, consider PostgreSQL-native enforcement as an additional backstop.

### Tests to add

```text
10:50–11:50 vs 11:00–11:30
10:30–12:00 vs 11:00–11:30
two different application processes
two different DB sessions
capacity=10, simultaneous party sizes 6 + 6
capacity=10, simultaneous party sizes 5 + 5
same practitioner
different practitioners
same room
different rooms
```

Run them against **PostgreSQL**, not SQLite.

# Phase 2 — Finish the reservation lifecycle

### Status: 🟡 PARTIAL

Creation/hold/commit is fairly substantial now. The service supports reservation holds, allocations, line-item snapshots, expiration and provider finalization.

But the generalized lifecycle isn't complete.

I found no proper generalized:

```text
cancel_reservation()
reschedule_reservation()
move_reservation()
change_party_size()
change_resource()
change_service()
change/add add-ons
```

The restaurant voice cancellation handler currently loads the reservation and directly changes:

```python
row.status = "cancelled"
db.commit()
```

rather than using a reservation-domain cancellation transaction.

That matters because a reservation may also have:

```text
Reservation
    │
    ├── ReservationResource
    ├── ReservationLineItem
    └── Appointment
             │
             └── Google Calendar event
```

All of those need consistent lifecycle handling.

### Implement

```text
cancel_reservation()
reschedule_reservation()
update_party_size()
change_resource_assignment()
add_line_item()
remove_line_item()
```

Each operation should have:

* idempotency,
* explicit state transitions,
* resource revalidation,
* price snapshot rules,
* provider synchronization,
* retries/reconciliation,
* audit event,
* notification behavior.

For example:

```text
CONFIRMED
    ↓
CANCEL_PENDING_PROVIDER
    ↓
Google delete
    ↓
CANCELLED
```

rather than immediately flipping a local status.

# Phase 6 — Fix and finish pricing

### Status: 🟡 PARTIAL

There is one concrete functional issue in the current price lookup.

`Price` supports `channel`, but:

```python
active_price(...)
```

does not accept or filter by channel.

So you could store:

```text
Haircut

web   €45
phone €50
walk-in €40
```

but `active_price()` may select the wrong one.

### Fix lookup precedence

Use something like:

```text
item
+
price book
+
location
+
channel
+
effective timestamp
```

Define deterministic fallback:

```text
exact location + exact channel
↓
exact location + generic channel
↓
generic location + exact channel
↓
generic location + generic channel
```

Also add validation for:

```text
Price.currency == PriceBook.currency
effective_until > effective_from
amount_minor >= 0
```

And detect overlapping competing prices.
