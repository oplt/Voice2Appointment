# Phase 3 — Customer dedup is much better, but has 4 important gaps

You now have:

* phone normalization;

* lowercase/trimmed email;

* org-scoped unique indexes;

* nested transaction retry;

* customer detail;

* reservation history;

* merge endpoint.

However:

### Gap 3.1 — migration can fail on existing duplicate customers

The new migration immediately executes:

```sql
CREATE UNIQUE INDEX ...
ON customer (organization_id, phone)
WHERE phone IS NOT NULL
```

and the equivalent email constraint.

But the previous application permitted duplicates.

So a production database containing:

```text
customer 41   +32470123456
customer 88   +32470123456
```

will fail during migration before the application can start.

You need a staged migration:

```text
1. normalize historical email/phone
2. identify duplicate groups
3. select canonical customer
4. move all references
5. archive/delete duplicate
6. verify no duplicates
7. create unique indexes
```

This is a **production-blocking migration issue**.

### Gap 3.2 — merge only migrates reservations

`merge_customers()` currently updates only `Reservation.customer_id`, then deletes the source customer.

But several other models reference Customer:

```text
Order.customer_id
SecureLinkDelivery.customer_id
PaymentIntent.customer_id
Reservation.customer_id
WaitlistEntry.customer_id
```

A real merge must reassign **all** of them.

Otherwise:

* some records become `NULL` because of `ON DELETE SET NULL`;
* waitlist deletion may encounter FK issues;
* customer history becomes fragmented.

This is probably the most important remaining domain-integrity bug.

### Gap 3.3 — `"US"` is hardcoded as the default phone region

Current normalization defaults to:

```python
default_region="US"
```

For an international SaaS supporting Belgian, German, Dutch, etc. organizations, a number such as:

```text
0470 12 34 56
```

must not be interpreted through US numbering rules.

Prefer:

```text
Organization
   ↓
Location.country_code
   ↓
default phone region
```

or require international `+countrycode` input when country context is unavailable.

### Gap 3.4 — “concurrency test” isn't actually concurrent

The test explicitly says it **simulates** a race by monkeypatching the first lookup to miss. It uses one SQLite session rather than two concurrent PostgreSQL transactions.

Add a genuine PostgreSQL test:

```text
Thread A                 Thread B
   │                        │
 lookup miss             lookup miss
   │                        │
 INSERT customer         INSERT customer
   │                        │
        unique constraint
             ↓
    one canonical row
```

### Gap 5.1 — changing price-book currency can violate your own invariant

`PATCH /price-books/{id}` permits:

```python
currency = "USD"
```

even when the price book already contains EUR prices.

You previously established the invariant:

```text
Price.currency == PriceBook.currency
```

After:

```text
PriceBook EUR
Price 25 EUR

PATCH PriceBook → USD
```

you get:

```text
PriceBook USD
Price 25 EUR
```

which contradicts the validation enforced during price creation.

Simplest safe behavior:

```text
if book already contains prices:
    currency cannot be changed
```

Otherwise you need an explicit currency migration—not merely relabeling the currency.

### Gap 5.2 — frontend doesn't appear to offer price-book editing

The backend has `PATCH /price-books/{id}`, but the Pricing screen exposes creation and archiving; I did not find a frontend `patchPriceBook` workflow.

So editing price-book name/state/currency is not end-to-end.

### Gap 6.2 — offset pagination is less robust for mutable reservations

The API now uses:

```text
ORDER BY start_datetime DESC, id DESC
OFFSET x LIMIT y
```

This is much better than the old fixed 200-row cap, but reservations can be rescheduled while an administrator is paging.

A reservation moving between page boundaries can create duplicate/missing results.

For a mature system I would eventually replace this with cursor pagination:

```text
cursor = (start_datetime, id)
```

This isn't a release blocker compared with CI/data integrity, but it is the more robust design.

# Revised remaining work

At this stage the list is much shorter than in the previous review. I would organize the next Codex cycle into **five phases**:

### Phase A — Make CI genuinely green

Refactor the eight oversized backend modules instead of raising architecture thresholds. Fix the `AppointmentsPage` pagination test so it tests pagination/dedup cheaply and deterministically. Then allow the entire pipeline to execute.

### Phase B — Harden customer identity

Implement a pre-unique-index duplicate migration; migrate **Reservation + Order + SecureLinkDelivery + PaymentIntent + WaitlistEntry** during customer merge; replace hardcoded US phone region with tenant/location country context; add a real multi-session PostgreSQL race test.

### Phase C — Finish admin UX

Complete resource edit/deactivation/force-warning, working-hours CRUD and time-off CRUD. Add price-book edit UI. Add reservation add-on/line-item add/remove UI.

### Phase D — Fix remaining pricing invariant

Prevent changing a price book's currency once prices exist, unless an explicit migration/conversion operation is implemented.

### Phase E — Production gate

Run real provider/service failure drills, get the entire GitHub Actions workflow green, then update `production-acceptance.md` from actual CI evidence rather than local claims.

So the project has moved from **“large architectural gaps” to “closure/integrity/verification gaps.”** The three issues I would treat as highest priority are **red CI**, **unsafe customer dedup migration/merge**, and **price-book currency consistency**.
